# 학습 계획 도구 중심 로드맵

상태: 2026-10-01 R4 및 기간 전체 분산 보완의 제작·통합 검증 결과를 독립 검토에 전달한다. 각 실행 근거와 미실행·한계는 아래 해당 절을 따른다. 독립 검토·사용자 최종 판단은 별도이며 이 문서의 단계는 아카이브의 과거 R/S 단계와 무관하다.

## 1. 목표와 확정된 범위

**LLM 없이도 구조화된 HTTP 요청으로 커리큘럼을 생성·수정·재편성하고 확정·저장할 수 있어야 한다.** LLM은 프론트가 전달한 사용자 요청을 해석해 같은 백엔드 도구를 사용하는 호출자다. 대화 ID·자연어 문장·mock 키워드는 학습 도구 실행의 필수 조건이 아니다.

- 현재 대상은 실제 카탈로그 강의의 다과목 일정이다. 복습 콘텐츠·문제 생성·진도/복습 기간 배분은 범위 밖이다. 향후 추가하면 강의와 같은 편성 대상 및 기한 조건으로 확장하되 지금 미리 구현하지 않는다.
- 과목당 30강·총 90강은 설명용 예시이며 고정 검증 수량이 아니다. 대표 검증에는 DB에 적재된 실제 EBSi 다과목 강좌의 강의 목록을 사용한다. 50분도 시간 축소 요청의 예시이지 모든 입력의 성공을 보장하는 값이 아니다.
- 새 과목은 기본적으로 기존 학생 계획에 통합한다. 기존 완료·피드백과 다른 학생 데이터는 보존한다.
- 도구 호출의 자유는 대화 시나리오에 종속되지 않는다는 뜻이다. 학생 범위·순서·시간·기한·revision 검증과 사용자 확인을 우회하는 자유는 아니다.

## 2. 세 가지 핵심 도구

아래는 책임 구분이다. 실제 함수명·URL·JSON 스키마는 1단계에서 정의한다.

| 도구 | 입력의 성격 | 동작·경계 |
| --- | --- | --- |
| 커리큘럼 생성 | 수강 강좌, 시작일·마감일, 가용 시간 | 전체 강의를 실제 날짜에 배치하는 최초 계획 계산 |
| 진도 조정 | 변경할 항목·날짜·적용 범위와 명시적인 수정 조건 | 제한된 범위를 변경하고 전체 제약 검증. 요청하지 않은 전체 재편성을 하지 않음 |
| 전체 재편성 | 현재 계획·완료 상태, 재편성 기준일, 남은 기한·가용 시간 | 완료 기록을 고정하고 남은 강의를 남은 기간에 균형 있게 다시 배치 |

조회·제안 확정·학습 완료/피드백 기록은 세 도구를 지원하는 공통 기능이다. 과목 추가·변경·제거와 기한·가용 시간 변경도 구조화된 요청으로 제공하되 별도 편성 알고리즘을 중복 구현하지 않는다.

### 부분 조정과 전체 재편성의 선택

예: 오늘의 국어001·영어001을 내일로 옮긴다는 명시적 요청을 진도 조정 도구로 전달한다. 가능한 경우 변경안과 영향을 반환한다. 순서 위반·시간 초과 등이 생기면 충돌 위치와 원인을 반환하고 현재 계획은 유지한다.

일반적인 시간 변경·미완료 이월에는 전체 재편성을 우선 사용한다. 부분 조정을 먼저 시도할 의무는 없다. 부분 조정은 오늘 수학과 내일 국어 교환 등 세밀한 명시적 수정용이다. LLM과 직접 API 호출자가 도구를 선택하며, 백엔드가 부분 조정 요청을 몰래 전체 재편성으로 바꾸지 않는다.

재편성은 미래의 기존 날짜 배치 보존보다 남은 학습의 순서·가용 시간·기한·분산을 우선한다. 단순히 내일로 이월 표시하거나 끝나는 날짜만 다시 추정하는 것은 재편성이 아니다. 최초 생성과 재편성은 공통 배치·검증 규칙을 사용하되 진도 조정은 별도 변경 경계를 갖는다.

### 공통 계약

- 입력: 학생·계획 식별, 기준 revision, 명확한 작업 범위와 구조화된 조건. 필요한 조건을 조용히 mock 값으로 채우지 않는다.
- 출력: 날짜별 강의·예정 시청 구간·순서·시간, 변경 전후 차이, 영향을 받은 날짜·항목, 기한 영향, 충돌·미지원·계산 한계. 과목 균형과 이월 우선순위는 아래 확정 정책을 따른다.
- 변경은 제안 → 별도 확정으로 처리한다. 제안은 저장해도 현재 계획·완료 상태는 바꾸지 않는다. 직접 API 사용자도 제안 ID와 기준 revision으로 확정할 수 있다.
- 확정은 제안의 학생·유효 상태·revision을 검증하고 원자적으로 저장한다. 재시도·동시 확정이 중복 변경을 만들지 않아야 한다.
- LLM은 도구 선택·해석·설명을 맡고, 편성 검증과 DB 변경은 백엔드가 맡는다. UI와 LLM이 별도 저장 경로를 갖지 않는다.

## 3. 단계별 구현과 인수 기준

각 단계는 통합 세션이 단일 인수 책임을 갖는다. 파트별 보고만으로 완료하지 않고 아래 결과를 직접 재현한다.

### 1단계 — 전체 일정 생성부터 API·DB까지

**결과:** LLM과 프론트 없이 첫 계획을 생성·확정·조회할 수 있다.

- 백엔드: 최소 입력·출력 계약, 실제 강의 기반 다과목 날짜 배치, 제약 검사, 전체/날짜별 조회, 생성 제안·확정 API.
- DB: 카탈로그 재사용 검토, 예정 일정과 완료 기록 분리, 계획 버전·제안·revision 저장. 필요한 최소 migration과 전용 테스트 DB.
- 프론트: 본격 재설계하지 않는다. 신규 API를 과거 화면에 억지로 맞추지 않는다.
- 통합: 기존 코드·DB의 재사용 경계를 정하고 실제 HTTP → 독립 SQL → 실제 서버 재시작 검증을 연결한다.

인수 기준:

1. DB에 적재된 EBSi 수학·국어·영어 강좌의 실제 편성 대상 강의 전체로 날짜별 계획을 생성한다. 실제 ID·길이·순서·가용 시간을 사용하며 30강씩 임의 절단하거나 부족한 강의를 만들어 채우지 않는다.
2. 다른 과목 수·강의 수·시간에서도 동작하며 항목 누락·중복·시간 초과가 없다.
3. 확인 전 학습 상태 불변, 확정 후 DB·API 일치와 재시작 복구를 확인한다.
4. 미지원·불가능·탐색 한계를 구분하고 실패를 성공 계획으로 저장하지 않는다.

### 2단계 — 진도 조정과 전체 재편성 분리

**결과:** 같은 계획을 대상으로 부분 수정과 남은 전체 일정 재계산을 각각 요청할 수 있다.

- 백엔드: 항목 이동·오늘만의 분량 조건·일시/지속 가용 시간 변경, 과목 추가·변경·제거, 기한 변경 계약. 학습 완료/피드백 기록과 독립적인 두 변경 도구 구현.
- DB: 완료·피드백을 보존하는 버전 전환, 조건 변경과 일정의 원자적 저장, 재시도·동시성·롤백·학생 격리 검증.
- 프론트: 계속 보류. HTTP 테스트가 도구의 직접 사용자가 된다.
- 통합: 부분 조정 영향 범위와 전체 재편성 결과가 구분되는 대표 시나리오를 실행한다.

인수 기준:

1. 일부 강의를 완료·부분 수강한 뒤 오늘 총한도 변경을 재편성으로 제안·확정한다. 평소 가용 시간과 실제 기록은 보존한다. 별도로 오늘·내일 강의 교환을 부분 조정하고 요청 밖의 배치가 유지되는지 검사한다.
2. 내일이 이미 가득 찬 입력에서는 충돌·영향을 반환하며 몰래 전체 재편성하지 않는다.
3. 이어 별도 재편성 요청을 보내 남은 기간의 날짜별 배치를 실제로 다시 만든다. 완료한 강의는 재배정하지 않는다.
4. 반복된 연기 뒤 재편성으로 순서·가용 시간·기한·분산 기준을 검증한다. 전후 결과가 동일해도 입력상 변경이 불필요했음을 설명할 수 있어야 한다.
5. 과목 추가·제거/변경·기한 변경을 확인 후 적용하며 과거 학습 이력은 지우지 않는다.
6. 오래된 제안·동시 확정·중복 피드백·학생 혼동·저장 중 실패를 검증한다. 완료 또는 부분 수강·당일 진행 시간이 바뀌면 이전 제안의 재검증 없이 확정하지 않는다.
7. 긴 강의의 다일 이어보기, 계획보다 덜 수강한 잔여 분량, 오래된 이월의 우선 배치와 이월 기준일 보존을 DB·API·실제 프로세스 재시작으로 검증한다. 계획 구간의 중복·누락·이미 수강한 구간 재배정과 진행 시간의 중복 가산을 차단한다.

**이 단계 종료가 LLM 독립 백엔드의 인수 지점이다.** 1·2단계가 부족하면 mock 대화나 화면으로 완료를 대체하지 않는다.

### 3단계 — 실제 LLM을 도구 호출자로 연결

**결과:** 자연어 요청을 동일한 검증된 도구 계약으로 처리한다.

- 백엔드: 대화 맥락과 누락 정보 질문, 구조화된 도구 호출, 결과 설명. 부분 조정과 재편성 선택은 LLM이 담당한다.
- DB: 대화 저장이 실제로 필요한 범위만 검토한다. 학습 저장 로직을 LLM 전용으로 복제하지 않는다.
- 프론트: 최소 대화 연결만 필요 범위에서 수행한다. 4단계는 이 화면의 기능 연결·검증을 보완하며 디자인 재설계는 별도 보류한다.
- 통합: 자연어 해석 실패와 도구 계산·저장 실패를 구분하고 기존 직접 API 회귀도 유지한다.

인수 기준: “오늘만 50분”, “앞으로 공부 시간을 줄여줘”, “영어 강의를 내일로”, “밀린 진도를 기한에 맞게 다시 나눠줘”, “국어도 추가해줘”를 구분한다. 불명확한 요청은 질문하고 도구가 반환한 충돌·계산 한계를 숨기지 않는다. 명시적 사용자 확인 없는 저장을 차단한다. 모델·키가 없어도 직접 도구 API는 계속 사용 가능하다.

### 4단계 — 최소 채팅 화면과 최종 통합

**결과:** 사용자가 생성·학습·조정·재편성·복구를 브라우저에서 완주한다.

- 프론트: 기존 실제 LLM 대화 화면을 우선 재사용한다. 채팅, 오늘 분량·날짜별 전체 계획의 간단한 표시, 변경 전후 비교·확정·보류, 부분 수강·완료/피드백 입력, 오류·재시도만 연결한다. 디자인 시스템·메인 데모 전면 재설계·새 영상 플레이어는 범위 밖이다. 실제 시청 자동 수집 없이 검증용 수동 학습 기록 입력을 사용할 수 있으며 이를 자동 시청 기록으로 표시하지 않는다.
- 의존성: 상대 경로 `/api`의 구조화 계약에만 의존한다. API 클라이언트·상태 처리와 화면 컴포넌트를 분리하고 백엔드는 화면 배치·컴포넌트를 알지 않도록 한다. 모델 답변 문장을 파싱해 기능을 실행하거나 프론트에서 편성·잔여 진도를 재계산하지 않는다. 향후 디자인 변경을 위한 대형 추상화 계층은 만들지 않는다.
- 백엔드·DB: 화면에서 드러난 계약·저장 문제를 보완하되 프론트에 계산을 떠넘기지 않는다.
- 통합: 실제 브라우저·HTTP·독립 DB·재시작 결과를 연결해 검증한다. 사용자 검토 후에만 병합을 요청한다.

인수 기준: 직접 API 검증과 같은 학습 결과가 화면에 표시된다. 오늘만의 변경과 전체 재편성의 차이 및 기한 영향을 사용자가 확인할 수 있고, 새로고침·오류 후에도 서버 정본을 유지한다.

R4 필수 검증:

1. 전용 DB·가상 학생과 실제 EBSi 카탈로그로 브라우저 → 실제 LLM → 도구 → 제안 표시 → 사용자 확정 → 독립 SQL을 연결한다. 생성, 과목 추가, 오늘 총시간·추가시간, 명시 교환 또는 충돌, 미완료 재편성을 확인한다.
2. 강좌 ID·구간 ID를 사용자 메시지에 주지 않는 자연어 요청에서 모델이 조회로 대상을 찾거나 모호하면 질문하는지 확인한다. 테스트 입력에 내부 ID를 미리 넣은 사례와 구분한다.
3. 부분 수강·완료·피드백을 화면에서 기록하고 재시도 중복 방지, 제안 후 진도 변경에 따른 오래된 확정 차단, 학생 전환 시 상태 분리, 실패 시 마지막 정상 상태 보존을 확인한다.
4. 확인 전 학습 상태 불변, 확인 후 화면·API·DB 일치, 새로고침 및 실제 서버 프로세스 재시작 복구를 검사한다. 대화 영구 저장은 요구하지 않으며 대화 초기화와 학습 데이터 복구를 구분해 안내한다.

### 검증 방식

검증은 기존 백엔드 테스트와 작은 HTTP 실행 스크립트를 우선한다. 작은 합성 입력은 경계값 단위 테스트에 보조적으로 쓸 수 있지만 실제 EBSi 카탈로그 기반 통합 검증을 대체하지 않는다. 자연어 시뮬레이터나 대형 검증 UI를 별도 제작하지 않는다. 예상 결과는 제품 함수를 그대로 재호출해 산출하지 않고 입력 항목 집합·시간·순서·변경 범위·DB 행을 독립 검사한다.

| 단계 | 상태 | 통합 인수·근거 |
| --- | --- | --- |
| 1. 생성·저장 | 통합 인수 검증 완료 | 실제 EBSi 126강·419939초의 직접 HTTP 생성·확정, 독립 SQL과 실제 OS 서버 재시작 복구 통과 |
| 2. 부분 조정·재편성 | 이번 합의 범위 마감, 재등록 별도 보류 | 날짜별 한도가 다른 이어보기·이월 우선순위 보완 및 회귀·통합 검증 완료. 재등록 세부 선택은 미결이며 422 유지 |

### 2026-09-30 R3 착수·인수 조건

사용자가 R3 구현과 실제 아주LLM 호출 검증을 승인했다. `.env.llm.local`의 설정 모델은 `gpt-6-luna`이며 키는 출력·복사·커밋하지 않는다. 기존 대화 페이지의 실제 응답은 사용자 확인이며 자동 도구 호출 검증 완료가 아니다.

실행 중 발견한 긴 강의 예정 이어보기 지연은 이월 다음 우선순위로 보완해 회귀를 추가했다. 기존 R4 화면 도구 테스트의20일·2강 입력은 첫날 배정을 전제로 했으므로2일 입력으로 바꾸고 예정/실제 표시 검사를 유지했다. 최종 실행에서는 위 검사 모두 통과했고 품질 허용치는 구현 결과에 맞춰 바꾸지 않았다.

한계·미실행: 제한된 탐색과 미래 총여유 확인은 모든 통강 조합의 배치 가능성이나 수학적 최적해를 증명하지 않는다. 선수·우선 이월·시작한 이어보기 때문에 앞쪽 분량과 공백이 생길 수 있으며 소수 강의의 매일 배정·마지막 날 완강을 강제하지 않는다. 이번 엔진 보완에서 실제 LLM·브라우저 경로를 다시 실행하지 않았고 추가 유료 호출은0회다. 요일 반복 조건·완료 후 부분 조정·재등록·디자인은 제외 상태다. 개발 DB·학생000·사용자 확정 계획·사용자 서버를 변경하지 않았으며 기존 계획은 별도 재편성 제안·명시 확인을 통해 적용해야 한다. `codex/fresh-start`/`a0034ae`와 기존 미커밋 변경을 보존했고 스테이징·커밋·브랜치 전환·병합·푸시는 하지 않았다.
