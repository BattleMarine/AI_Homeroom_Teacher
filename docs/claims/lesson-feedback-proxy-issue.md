# 강의별 체크 API 전달 실패 클레임

## 목적

프론트엔드의 `AI 담임에게 전달하기` 동작에서 강의별 체크 기록이 실패하는 현상을 백엔드 개발 세션과 공유합니다.

이 문서는 현재 확인된 API 계약, 프론트 호출 방식, 재현 결과, 관찰 로그, 추정 원인을 기록합니다. 실제 도메인, 포트, 키, 토큰은 포함하지 않습니다.

## 사용자 증상

더미 강의 화면에서 이해도와 집중도를 선택한 뒤 `AI 담임에게 전달하기`를 누르면 다음 오류가 표시됩니다.

```text
기록을 전달하지 못했습니다. 백엔드 연결을 확인한 뒤 다시 시도해 주세요.
```

이 오류가 발생하면 프론트엔드는 학습 기록을 반영하지 않고, 다음 강의 추천 흐름으로 이동하지 않습니다.

## 프론트엔드 호출 방식

호출 위치:

```text
src/app/App.tsx
  completeMockLesson()

src/api/teacher-api.ts
  recordLessonFeedback()
```

사용 API:

```text
POST /api/lesson-feedback
Content-Type: application/json
```

요청 본문 형식:

```json
{
  "lessonId": "stable-log-graph-asymptote-lecture",
  "understandingLevel": 3,
  "focusLevel": 3
}
```

프론트엔드는 `recorded: true` 응답과 `teacherNote`를 받으면 학습 기록을 저장하고, 진행 보고 카드에 백엔드의 안내 문구를 표시합니다. HTTP 응답이 성공 범위가 아니거나 JSON으로 해석할 수 없으면 오류를 표시하고 기록 처리를 중단합니다.

## 기대 계약

```json
{
  "dataSource": "mock",
  "responseType": "mock",
  "lessonId": "stable-log-graph-asymptote-lecture",
  "recorded": true,
  "teacherNote": "강의별 응답을 기록했고, 다음 수업 조율에 반영하겠습니다."
}
```

## 실행 결과와 로그

확인 시점에 백엔드 서버의 상태 API와 강의별 체크 API를 직접 호출했습니다.

| 확인 경로 | 요청 | 결과 |
| --- | --- | --- |
| 백엔드 직접 호출 | `GET /api/health` | `200`, JSON 응답, `status: "ok"` |
| 백엔드 직접 호출 | `POST /api/lesson-feedback` | `200`, JSON 응답, `recorded: true` |
| 프론트 개발 서버 경유 | `POST /api/lesson-feedback` | `404`, 요청 실패 |

직접 호출 응답 로그:

```json
{
  "dataSource": "mock",
  "responseType": "mock",
  "lessonId": "stable-log-graph-asymptote-lecture",
  "recorded": true,
  "teacherNote": "강의별 응답을 기록했고, 다음 수업 조율에 반영하겠습니다."
}
```

프론트 개발 서버 경유 로그:

```text
POST /api/lesson-feedback
HTTP 404
```

프론트의 공통 API 클라이언트는 `response.ok`가 거짓이면 다음 오류를 발생시키고, 화면은 이를 사용자용 오류 문구로 전환합니다.

```text
AI 담임 API 요청에 실패했습니다.
```

## 추정 원인

백엔드 라우트와 요청 본문은 직접 호출에서 정상 동작하므로, 현재 관찰만으로는 백엔드 핸들러의 결함으로 보기 어렵습니다.

가장 가능성이 높은 원인은 프론트 개발 서버의 `/api` 프록시가 적용되지 않은 것입니다.

```text
Vite 설정은 API 프록시 대상 환경 변수가 있을 때만 /api 프록시를 등록한다.
프론트 개발 서버가 해당 환경 변수 없이 실행되었거나,
환경 변수 반영 전 서버가 계속 실행 중이면 POST /api/lesson-feedback가 백엔드로 전달되지 않는다.
이 경우 개발 서버 자체가 경로를 처리하지 못해 404를 반환한다.
```

## 백엔드 확인 요청

현재 계약 자체는 정상 응답을 확인했습니다. 백엔드 세션에서는 다음 항목을 확인해 주세요.

1. `POST /api/lesson-feedback`가 현재와 같은 요청 본문을 계속 허용하는지 확인합니다.
2. 성공 응답의 `recorded`와 `teacherNote` 필드를 API 계약으로 유지합니다.
3. 앱 주입 테스트로 정상 본문에 대한 `200`과 잘못된 본문에 대한 검증 오류를 고정합니다.
4. 로컬 실행 문서에서 API 서버 기동 뒤 프론트 개발 프록시를 재시작해야 한다는 점을 명확히 안내합니다.

## 프론트엔드 조치

프론트엔드는 서버 주소를 코드에 직접 넣지 않습니다. 개발 서버를 로컬 비밀 문서에 정의된 프록시 환경 변수와 함께 다시 실행하면, `/api/lesson-feedback` 요청이 백엔드로 전달되어야 합니다.

백엔드의 라우트 접두사나 요청·응답 계약이 변경되면, 이 문서와 `src/api/teacher-api.ts`를 함께 갱신합니다.

## 재시도 결과

클레임 문서를 작성한 뒤 동일한 요청 본문으로 한 번 더 확인했습니다.

| 확인 경로 | 결과 | 판정 |
| --- | --- | --- |
| 백엔드 직접 `POST /api/lesson-feedback` | `200`, JSON 응답, `recorded: true` | 정상 |
| 프론트 프록시 `POST /api/lesson-feedback` | `404` | 실패 재현 |

재시도 프록시 로그:

```text
POST /api/lesson-feedback
HTTP 404
원격 서버에서 (404) 찾을 수 없음 오류를 반환했습니다.
```

두 번째 실행에서도 백엔드 직접 호출은 정상이고 프론트 프록시 요청만 실패했습니다. 따라서 현재 우선 조치 대상은 백엔드 핸들러가 아니라 프론트 개발 서버의 API 프록시 환경 변수 적용 여부와 서버 재시작 상태입니다.

## 해결 조치

프론트 개발 서버가 `API_PROXY_TARGET` 없이 조용히 시작하면 `/api/*` 요청이 Vite 자체의 404로 끝나는 문제가 있었습니다.
다음 조치로 해결합니다.

```text
로컬 Git 제외 .env.local에 API_PROXY_TARGET을 기록
Vite 시작 시 API_PROXY_TARGET이 없으면 즉시 오류로 중단
강의별 체크 API의 Fastify 앱 주입 테스트 추가
```

이후 프론트 개발 서버를 재시작하면 `/api/lesson-feedback` 요청은 API 서버로 프록시됩니다.
프론트 서버를 재시작하지 않으면 기존 Vite 설정이 유지되므로, 환경 파일을 만든 뒤에도 반드시 재시작해야 합니다.

## 백엔드 응답

### 현재 상태

`investigating` — 백엔드와 프록시 설정 조치는 완료했습니다. 프론트 개발 서버 재시작 뒤 실제 화면에서의 재확인이 남아 있습니다.

### 원인 판정

`POST /api/lesson-feedback`의 백엔드 핸들러와 요청·응답 계약은 정상입니다.
직접 호출과 앱 주입 테스트에서 아래 요청은 성공합니다.

```json
{
  "lessonId": "stable-log-graph-asymptote-lecture",
  "understandingLevel": 3,
  "focusLevel": 3
}
```

실패 원인은 프론트 개발 서버가 `API_PROXY_TARGET` 없이 실행되어 `/api/*` 프록시를 등록하지 않은 점입니다. 이 상태에서는 상대 경로 요청이 API 서버가 아닌 Vite 개발 서버에 도착하고, Vite가 `404`를 반환합니다.

### 적용 완료한 조치

```text
Git 제외 .env.local에 API_PROXY_TARGET 추가
개발 모드에서 API_PROXY_TARGET이 없으면 Vite 시작을 중단하도록 변경
강의별 체크 API의 정상·검증 오류 앱 주입 테스트 추가
README와 백엔드 API 기반 문서에 프록시 재시작 절차 추가
```

백엔드 API 계약은 변경하지 않았습니다. 프론트의 `recordLessonFeedback()`은 현재 요청 본문과 응답 필드를 그대로 사용하면 됩니다.

### 프론트엔드 필수 조치

1. 실행 중인 프론트 개발 서버를 종료합니다.
2. 프로젝트 루트에서 프론트 개발 서버를 다시 실행합니다.

```bash
pnpm dev
```

3. 더미 강의에서 이해도와 집중도를 선택한 뒤 `AI 담임에게 전달하기`를 다시 실행합니다.
4. 브라우저 개발자 도구의 네트워크 탭에서 아래 조건을 확인합니다.

```text
요청 경로: /api/lesson-feedback
요청 메서드: POST
응답 상태: 200
응답 본문: recorded가 true이고 teacherNote가 존재함
```

프론트 코드는 API 서버의 실제 주소나 포트를 직접 사용하지 않고, 현재처럼 상대 경로 `/api`만 호출해야 합니다.

### 프론트엔드 후속 개선 제안

이번 오류처럼 연결 실패가 사용자에게 모두 같은 문구로 보이지 않도록, 프론트는 다음을 추가하는 편이 좋습니다.

```text
앱 시작 시 getApiHealth()를 호출해 API 연결 상태를 화면 상태로 관리
강의별 체크 전송 중에는 전달 버튼을 비활성화해 중복 요청 방지
실패 시 재시도 버튼을 제공하고, 개발 환경에서는 상태 코드와 요청 경로를 콘솔에 기록
API 연결 실패와 요청 본문 검증 실패를 서로 다른 사용자 안내 문구로 표시
```

이 개선은 백엔드 API 계약 변경 없이 `src/api/teacher-api.ts`와 강의별 체크 UI에서 진행할 수 있습니다.

### 재확인 기준

프론트 개발 서버를 재시작한 뒤 같은 요청이 `200`과 `recorded: true`를 반환하면 이 클레임은 해결된 것으로 처리합니다. 재시작 뒤에도 실패하면 프론트는 네트워크 요청 경로, 상태 코드, 응답 본문을 이 문서의 새 섹션에 추가합니다.

## 프론트엔드 후속 조치

백엔드 응답을 반영해 프론트 API 클라이언트가 HTTP 상태와 응답 형식 오류를 구분하도록 보강했습니다. 개발 환경에서는 실패한 요청의 경로와 상태 코드만 브라우저 콘솔에 기록합니다. 요청·응답 본문과 환경 변수 값은 기록하지 않습니다.

강의별 체크 화면과 앱 시작 API 확인 화면은 이제 다음 상황을 구분해 안내합니다.

```text
404: 프론트 개발 서버의 API 프록시가 반영되지 않은 상태
400: 강의별 체크 요청 형식이 API 계약과 다른 상태
성공 응답이 JSON이 아님: 프록시 또는 API 서버가 예상과 다른 응답을 반환한 상태
그 외 연결 오류: API 서버 연결을 확인해야 하는 상태
```

현재 실행 중인 프론트 개발 서버로 동일 요청을 다시 확인한 결과는 여전히 `404`입니다. 이는 실행 중인 Vite 프로세스가 새 프록시 설정을 읽기 전 상태임을 뜻합니다. 소스 수정만으로 이미 실행 중인 개발 서버의 프록시를 갱신할 수는 없으므로, 프로젝트 루트에서 프론트 개발 서버를 종료한 뒤 `pnpm dev`로 다시 시작한 후 재검증이 필요합니다.
