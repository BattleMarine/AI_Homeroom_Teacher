# 클레임 협업 규칙

## 목적

프론트엔드와 백엔드가 서로의 경계에서 문제를 발견했을 때, 재현 가능한 기록과 같은 문서 안의 응답으로 해결 과정을 이어 갑니다.
클레임 문서는 단순 오류 메모가 아니라 담당 세션 간의 작업 인수인계 기록입니다.

## 작성 흐름

```text
문제 발견 담당자가 docs/claims/에 클레임 문서를 작성
다른 담당자가 문서의 재현 정보와 계약을 확인
원인 분석과 수정 작업 수행
같은 문서 마지막에 담당 영역의 응답과 다음 조치를 추가
문서를 작성한 담당자가 재확인 결과를 같은 문서에 추가
해결 또는 추가 조사 상태를 명시
```

기존 내용을 수정하거나 지우지 않고, 시간 순서대로 새 섹션을 덧붙입니다. 이렇게 해야 원인 추적과 계약 변경 이력을 유지할 수 있습니다.

## 최초 클레임 작성 형식

```md
# 기능 또는 API 이름 클레임

## 상태

open

## 사용자 증상

사용자 화면에서 보이는 현상과 영향

## 재현 절차

1. 재현에 필요한 화면 또는 요청
2. 입력값
3. 실제 결과

## 기대 결과

기대하는 화면 또는 HTTP 응답

## 관찰 로그

요청 메서드, 상대 경로, 상태 코드, 오류 응답

## 상대 담당자 확인 요청

계약, 데이터, 설정 중 확인이 필요한 질문
```

## 응답 작성 형식

문서를 받은 담당자는 같은 파일 마지막에 아래 형식으로 답합니다.

```md
## 프론트엔드 응답 또는 백엔드 응답

### 원인 판정

확인한 사실과 원인

### 적용한 조치

수정한 파일과 계약 변경 여부

### 상대 담당자 조치

재시작, 호출 방식, 화면 처리 등 다음 담당자가 할 일

### 재확인 기준

성공으로 판단할 HTTP 상태, 응답 필드, 화면 동작
```

## 기록 원칙

- 실제 도메인, 포트, API 키, 토큰, 개인정보는 적지 않습니다.
- 요청은 상대 경로와 비밀값이 제거된 본문만 기록합니다.
- HTTP 상태 코드와 응답의 핵심 필드는 반드시 남깁니다.
- API 계약이 바뀌면 클레임 문서뿐 아니라 API 기준 문서와 호출 클라이언트도 함께 갱신합니다.
- 재확인 전에는 해결됐다고 단정하지 않고, 상태를 `open`, `investigating`, `resolved` 중 하나로 표시합니다.
